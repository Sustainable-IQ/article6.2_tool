# Purpose of this document

This is a complete handover from the first working session. It carries the project definition, everything produced, the verified calculation logic, the findings, the architecture decision, the open questions, and the exact next steps. A new session should be able to start from this file alone and lose nothing.

# The objective

Convert the Gold Standard and Verra Article 6.2 Corresponding Adjustments Reporting Tool, currently an Excel workbook, into an online tool with a backend and a frontend running on Cloudflare, and produce the market positioning content that goes with it.

Positioning agreed: neutral free public utility with light SustainableIQ attribution. Audience: anyone who needs to use the tool, in practice host country designated national authorities preparing the 2026 Biennial Transparency Report, plus project developers, buyers, analysts, and review teams.

Deadline pressure: second Biennial Transparency Reports are due 31 December 2026. The source workbook has a data cutoff of 14 August 2026, so it is already incomplete and will get more so.

Resources provided: GitHub repository `https://github.com/Sustainable-IQ/article6.2_tool` (currently empty) and Cloudflare account `5523ce34c91c1ae9a01d0d2742fd8ecd`.

# What the source workbook is

`Article-6.2-CA-Reporting-Tool_v1.xlsx`, version 1.0, dated 20 August 2026, data cutoff 14 August 2026. Created by David Hynes (Gold Standard), last edited by Liz Guinessey (Verra). Announced publicly on 20 August 2026 (1).

Six sheets: `Introduction`, `Structured Summary`, `Detailed Credit Data`, `Country List`, `Notes`, `Change Log`.

It takes a country plus four accounting settings and produces Table 4 of the annex to Decision 5/CMA.3, the structured summary a Party submits alongside its Biennial Transparency Report.

## What it is really doing

Three things, worth keeping in mind while building the replacement.

It is reverse information flow. Governments issue authorisations, then the units live on private registries where the government does not track issuance or transfer. So the operational record of a sovereign accounting obligation sits inside two programmes' databases, and this workbook is those programmes telling fourteen governments what those governments authorised.

It is a reconciliation between two records that disagree, not a registry extract. The cover text states that credits may be authorised while developers have not yet requested Article 6 labels on the registries, so the file contains units the registries do not show as authorised. This dataset cannot be rebuilt by scraping either registry.

It is a liability statement. Row 12 debits the national account and row 14 restates the country's emissions after that debit. The workbook's own instructions describe the deliverable as "the emissions balance to be reported".

# Verified calculation logic

The engine was reimplemented independently in Python and reconciles exactly to the workbook's own cached values across every calculated row. Treat the following as the specification. It is verified, not inferred.

## Inputs

Five configuration answers:

| Setting | Values |
|---|---|
| Country | One of the 14 in the dataset. Free text in the workbook, which is a defect |
| NDC target type | Single-year or Multi-year |
| Accounting method | Single-year: Averaging or Annual Adjustments/Trajectory. Multi-year: Annual Adjustments/Trajectory only |
| Latest GHG inventory year in BTR 2026 | 2021 through 2025 |
| Authorisation scope | All, or Uploaded to the CARP only |

Five manual numeric rows, each with a value per year 2021 through 2026: rows 3, 4, 5, 6 and 9.

Important: of rows 3 to 6, which the instructions ask the user to fill, only row 5 is consumed by any formula. Rows 3, 4 and 6 pass through to the submission and feed nothing. Row 9, which the instructions never mention, feeds rows 10 and 12.

## Scope filter

Applied to every aggregation. Scope `All` applies no filter (the workbook passes `"*"` as the SUMIFS criterion, which matches any non-empty text in the CARP column). Scope `CARP` filters to rows where `Authorisation uploaded to the CARP = "Yes"`.

## Row by row, for each year Y and country X

Let `pool` be all credit blocks where `Country = X` and the scope filter passes.

**Row 7, annual quantity of ITMOs first transferred**

    sum(Volume) over pool where NDC = "Yes" and FirstTransferDefinition = "Authorisation" and AuthorisationYear = Y
  + sum(Volume) over pool where NDC = "Yes" and FirstTransferDefinition = "Issuance"      and IssuanceYear      = Y

**Row 8, mitigation outcomes authorised for (O)IMP only**

Identical to row 7 with `NDC = "No"`.

**Row 9**: user input.

**Row 10**: `(Row7 + Row8) - Row9`.

**Row 11, cumulative ITMOs divided by elapsed years**

    if TargetType = "Multi-year" or Method = "Annual Adjustments/Trajectory":  "N/A"
    else if Method = "Averaging" and InventoryYear is set and Y <= InventoryYear:
        sum(Row10 across all six years) / count(years <= InventoryYear)
    else: blank

**Row 12, total corresponding adjustments**

    if TargetType = "Single-year" and Method = "Averaging":  Row11[Y]
    else:  sum(Volume) over pool where Vintage = Y   minus   Row9[Y]

Note carefully: in the else branch there is no filter on NDC status and no filter on first transfer definition. Rows 7 and 8 key on the year of first transfer over a filtered population; row 12 keys on vintage year over the whole national population. They are different populations, not two views of one.

**Row 13**: running cumulative total of row 10 from 2021 up to and including Y.

**Row 14, annual emissions balance**

    if Row12[Y] is numeric and Y <= InventoryYear:  Row5[Y] - Row12[Y]
    else: blank

# Findings, in order of importance

## 1. Authorised but unlabelled credits

The workbook's cover text states that credits may be authorised while developers have not yet requested Article 6 labels on the programme registries. Consequence: a unit can be sold into the voluntary market as an ordinary VER while the host country still owes a corresponding adjustment on it. The government carries the debit, the buyer never treated the unit as an ITMO, and nothing on the registry flags the mismatch. This is systemic and affects both sides of every trade. The tool should make this visible.

## 2. Authorisation terms are not modelled

The cover text tells countries to "ensure that volume of corresponding adjustments is consistent with the terms of the authorisation". The workbook holds no cap, window, vintage restriction or condition field. It can therefore compute an adjustment larger than the authorisation permits, and its remedy is a sentence asking the user to check by hand against the legal instrument. Encoding authorisation terms and flagging breaches is the single clearest functional improvement available.

## 3. The two halves of the summary run on different clocks

Corresponding adjustments key on vintage. First transfers key on authorisation or issuance year. Across the whole dataset:

| Year | By vintage (row 12) | By first transfer (rows 7 and 8) | Gap |
|---|---|---|---|
| 2021 | 1,584,413 | 0 | -1,584,413 |
| 2022 | 4,619,796 | 2,827 | -4,616,969 |
| 2023 | 8,242,874 | 7,209,605 | -1,033,269 |
| 2024 | 8,120,374 | 6,935,940 | -1,184,434 |
| 2025 | 673,393 | 5,457,177 | +4,783,784 |
| 2026 | 0 | 3,635,301 | +3,635,301 |

Adjustments land in 2021 to 2024, against inventory years already reported or about to be. The ITMO flows those same countries report sit in 2025 and 2026. Only 2.9% of volume carries a vintage of 2025 or later. This is a retroactive exercise dressed as a current one and it affects every country.

## 4. The CARP scope switch is the largest single lever

46% of volume sits under authorisations not uploaded to the CARP. Restricting to CARP-only takes five countries to zero and cuts Rwanda by 81%. It is presented as an ordinary dropdown with no warning.

## 5. Both citations for the accounting choice are wrong

The `Introduction` sheet cites "Paragraph 7 of the annex to Decision 3/CMA.3". The `Structured Summary` sheet cites "paragraph 7 of the Annex to decision Decision 5/CMA.3". They disagree with each other and neither is right. Decision 3/CMA.3 governs the Article 6.4 mechanism; Decision 5/CMA.3 governs transparency modalities. The provision is Decision 2/CMA.3, annex, paragraph 7(a) (3), confirmed against the UNFCCC Article 6.2 Reference Manual (4).

## 6. Smaller defects

Row 9 is an undeclared input that changes the answer. The country field is unvalidated free text, so a typo returns a page of clean zeros with no error. The first transfer dropdown offers "Authorisation, Issuance, Use" while the data contains "First international transfer" and no "Use". The vintage dropdown skips rows 230 to 586, exactly the Verra block. Freeze panes sit at row 252 rather than under the header. 601 rows contain 600 distinct serial numbers.

## 7. Gambia and Sierra Leone

Their "First international transfer" definition matches neither SUMIFS in rows 7 and 8, so those rows return zero, but row 12 has no first transfer filter and returns 196,652 and 2,078 respectively. The resulting structured summary shows zero first transfers alongside a non-zero adjustment, which is internally inconsistent.

A note for the next session: this is real but it is 0.9% of the dataset. In the first session it was allowed to dominate the framing, which was a mistake. It belongs in the defect list, not in the value proposition.

# Architecture decision

Agreed direction, with two questions still open.

One Cloudflare Worker serving both the API and the frontend through Workers static assets. One deploy, one domain, no CORS, no separate Pages project.

D1 as the backend store: credit blocks, dataset snapshots, countries, programme notes, and later authorisation terms. This is what makes data currency solvable structurally rather than by redistributing a file.

A hard privacy split. Public data (credit blocks, aggregates, notes) comes from the API. The country's own figures (inventory, trajectory, ITMOs used) never leave the browser. The same engine module runs in both places.

Proposed repository layout:

    wrangler.jsonc                Worker, D1 binding, assets binding
    migrations/0001_schema.sql
    data/snapshots/2026-08-14/credits.json
    data/seed/2026-08-14.sql      generated INSERT statements, 601 rows
    src/index.js                  Worker entry: /api/* plus static assets
    shared/engine.js              calculation engine, browser and worker
    public/index.html app.js styles.css
    test/engine.test.js           reconciles to the workbook fixture
    tools/ingest.py               xlsx to snapshot json to seed sql
    README.md

Proposed API for v1: snapshots, countries, credits by country and scope, summary, market aggregate, notes.

## Open questions

1. D1, or versioned JSON in the repo? D1 is a real backend and makes updates a data operation. JSON is simpler and makes every update a redeploy. Not yet decided.
2. Framework or not? The first session proposed plain ES modules with no bundler, partly because npm was unavailable in that sandbox and partly because the app is a config form, a table and a detail panel. On the MacBook the constraint disappears, so this should be decided on merit. Zero dependencies buys fast loads for low-bandwidth users and a tool that still builds in three years.
3. Coverage. Gold Standard and Verra only, or a data model with source and confidence fields ready to absorb ART, ACR, CAR, Article 6.4 units, bilateral arrangements and national registries? Costs little now, changes what the tool can become.
4. Scenario comparison as a first-class feature or a later addition? Averaging against trajectory and one first transfer reading against another are the largest levers in the whole exercise and the Excel cannot show them side by side.
5. Whether to notify David Hynes and Liz Guinessey of the defects before or at publication. Current direction is to publish the corrected engine and document the divergence at launch.

## Script inventory

`extract.py` parses the workbook twice with openpyxl, once for cached values and once for formulas, and emits `credits.json`, `credits.csv` and `tool_meta.json`. The metadata file captures the cover text, all twelve Table 4 row labels verbatim, every explanation from column H, every data validation list, the country notes and the change log. Re-run it against any future workbook release to produce a new snapshot.

`engine.py` is the verified calculation engine plus the reconciliation harness that produced the fixture and regression tables above. Port this to TypeScript or JavaScript first; everything else depends on it.

`app/template.html` exists in the session workspace only. It is an untested prototype shell covering the layout, configuration controls, editable summary grid, cell-level drill-down, scope comparison, sign-off checklist and CSV export. It was never compiled with data and never opened in a browser. The layout is reusable as scaffolding. Its alert panel leads with the Gambia defect and should be rewritten. Do not trust it until it runs.

# Environment constraints hit in the first session

Verified, not assumed:

- `npm install` returns HTTP 403 for every package. No Vite, TypeScript, wrangler, or test runner could be installed.
- Pushing to `Sustainable-IQ/article6.2_tool` is refused by the session git proxy: the repository is not in the session's authorized repository set. Anonymous read works; the repository is empty.
- No Cloudflare access of any kind.
- The Google Drive connector cannot accept text payloads above roughly 50 KB and has no binary or resumable upload path.

A session on the MacBook with a connected folder removes the first three, since commands run on the local machine under local credentials. Note that each `device_bash` call in Cowork has a ceiling around 45 seconds, so installs and builds need splitting into steps. Claude Code in VSCode has no such limit and may suit the build phase better.
